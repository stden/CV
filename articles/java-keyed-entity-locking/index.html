Java Concurrency and Keyed Entity Locking

Designing per-entity mutex synchronization in JVM memory using ConcurrentHashMap, per-key ReentrantLock instances, and canonical key ordering — plus an honest look at lock-registry eviction races.

Independent engineering write-up grounded in the public stden/EntityLocker repository; no employer code or production metrics.

Why Keyed Locking Instead of a Global Lock

When in-memory workers update domain aggregates keyed by entity ID, coarse synchronization on a shared collection serializes unrelated entities and limits throughput.

A keyed lock registry maintains one ReentrantLock per active key in a ConcurrentHashMap so threads operating on distinct IDs proceed concurrently while threads targeting the same ID coordinate cleanly.

ReentrantLock lock = locks.computeIfAbsent(key, k -> new ReentrantLock());
lock.lock();
try {
    work.run();
} finally {
    lock.unlock();
}

Preventing Deadlocks Across Multiple Keys

If Thread A locks entity 10 then 20 while Thread B locks 20 then 10, lock-order inversion triggers a classic deadlock.

Sorting keys canonically before acquisition establishes a strict global total order across threads. Because ReentrantLock is reentrant per thread, deduplicating identical keys or acquiring in ascending comparable order eliminates two-key cycles.

Engineering Trade-offs

  • Per-key in-memory locks avoid database round-trips for single-JVM coordination, but provide zero protection across multiple application replicas (distributed workloads require database row locks or external leases).
  • Keeping lock entries forever leaks memory on unbounded ID spaces, whereas eager eviction introduces race conditions if not synchronized atomically with reference counts.

Limitations & Boundaries

  • In public stden/EntityLocker, CountLock maintains an enter counter separately from map removal, creating a documented non-atomic race under simultaneous acquire and eviction.
  • EntityLocker includes JUnit 4 tests in src/test/java/EntityLockerTest.java but does not yet configure an automated GitHub Actions CI workflow.

Reproducible Verification

Clone stden/EntityLocker and run its Maven/JUnit test suite locally under two concurrent stress scenarios (same-key contention vs swapped multi-key acquisition).

git clone https://github.com/stden/EntityLocker.git
cd EntityLocker && mvn test
