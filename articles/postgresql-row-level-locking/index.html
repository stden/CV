PostgreSQL Row-Level Locking for Concurrent Worker Queues

Comparing SELECT FOR UPDATE, NOWAIT, and FOR UPDATE SKIP LOCKED when implementing multi-worker job claims on top of a relational database.

Independent PostgreSQL concurrency note using reproducible standard SQL; excludes employer schemas and non-public benchmarks.

Blocking vs Non-Blocking Claim Queries

Naive SELECT followed by UPDATE lets two workers claim the same queued row concurrently. Adding FOR UPDATE prevents double claims, yet causes subsequent workers to block waiting on the first worker's transaction commit.

Adding SKIP LOCKED allows each concurrent worker session to atomically claim the next unlocked eligible row without waiting on rows locked by active transactions.

WITH next_job AS (
  SELECT id FROM job_queue
  WHERE status = 'PENDING' AND run_at <= CURRENT_TIMESTAMP
  ORDER BY run_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE job_queue q
SET status = 'CLAIMED', claimed_at = CURRENT_TIMESTAMP
FROM next_job
WHERE q.id = next_job.id
RETURNING q.id;

Engineering Trade-offs

  • SKIP LOCKED simplifies transactional enqueue-with-domain-state without operating a dedicated broker, but high update churn creates dead tuples requiring tuned autovacuum.
  • Holding transactions open during external HTTP calls exhausts database connections; fast claim-to-LEASED transactions with visibility timeouts scale much better.

Limitations & Boundaries

  • Relational queues do not match dedicated log brokers like Apache Kafka for multi-consumer fan-out or high-throughput event replay.
  • Reproducible experiment tests lock semantics rather than production cluster sizing.

Reproducible Verification

Open two psql sessions on the same PostgreSQL database, execute the CTE claim without committing in Session 1, and observe Session 2 claim row 2 immediately.

Session 1: BEGIN; SELECT id FROM job_queue WHERE status = 'PENDING' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;
Session 2: BEGIN; SELECT id FROM job_queue WHERE status = 'PENDING' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;
