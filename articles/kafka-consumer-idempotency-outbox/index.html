Kafka Consumer Behaviour, Idempotency, and the Transactional Outbox

Why consumer rebalances and dual writes break naive event pipelines, how partitioned key ordering interacts with retry topics, and where transactional outbox plus idempotent consumers restore safety.

Independent educational analysis of Apache Kafka delivery semantics and outbox patterns; contains no employer topology or proprietary broker configuration.

At-Least-Once Delivery Across Consumer Rebalances

When a Kafka consumer processes a batch, writes side effects to a database, and crashes before committing offsets, the next rebalance replays those records to another consumer instance.

Even with enable.auto.commit=false and manual acknowledgment, network timeouts or poll interval expiry (max.poll.interval.ms) can evict a consumer mid-batch and cause duplicate delivery.

Avoiding Dual Writes with Transactional Outbox + Idempotency

Updating local state and calling producer.send() in separate steps creates a dual-write window where one succeeds and the other fails. Writing both the domain change and an outbox row inside one ACID database transaction closes that window.

On the consumer side, persisting a deterministic event_id in a deduplication table (with a unique constraint) in the same local transaction guarantees idempotent state transitions even across broker retries or consumer rebalances.

INSERT INTO processed_events (event_id, processed_at)
VALUES (:eventId, CURRENT_TIMESTAMP)
ON CONFLICT (event_id) DO NOTHING;

Engineering Trade-offs

  • Non-blocking retry topics avoid stalling healthy keys behind a single poison pill, but weaken strict per-key ordering while a failing key sits in a delayed retry topic.
  • CDC-based outbox publishing (e.g., log tailing) reduces polling load compared to database polling relays, at the cost of extra connector operational complexity.

Limitations & Boundaries

  • Deduplication tables grow over time and require bounded retention aligned with Kafka topic retention or downstream replay windows.
  • Examples are vendor-neutral educational patterns and exclude employer-specific topic names, partition counts, or SLAs.

Reproducible Verification

Verify idempotent deduplication in any local PostgreSQL instance by simulating a replayed event batch inside a transaction that aborts after state mutation but before offset acknowledgement.

CREATE TABLE processed_events (event_id UUID PRIMARY KEY, processed_at TIMESTAMPTZ NOT NULL);
Run duplicate INSERT ... ON CONFLICT (event_id) DO NOTHING and verify row count stays 1.
