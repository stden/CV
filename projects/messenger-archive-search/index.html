Personal project

Messenger Archive & Semantic Search

A searchable archive of a personal messenger history, with voice messages transcribed and indexed, exposed to LLM agents through an MCP server.

Engineering context: Personal project

Problem

A long personal messenger history is hard to search. Voice messages need to be searchable as text too.

Architecture

A Rust sync service pulls the history over MTProto into PostgreSQL. A Python worker claims transcription jobs with SKIP LOCKED and runs Whisper. A Rust indexer creates embeddings in batches and upserts them into Qdrant with deterministic UUIDv5 point IDs. An MCP server exposes search to LLM agents.

Architecture diagram

  1. Messenger account. The source of messages.
  2. Sync service (Rust). Writes messages and chats to PostgreSQL.
  3. PostgreSQL. The system of record for the archive.
  4. Transcription worker (Python). Lets several workers share one queue.
  5. Indexer (Rust). Builds the vector index.
  6. Qdrant. Stores embeddings; the same message always maps to the same point.
  7. MCP server. The interface for LLM agents.

Component names are generic. Concepts used here: idempotency, eventual consistency, distributed coordination, failure handling.

Technology stack

  • Rust
  • Python
  • MTProto
  • Whisper
  • PostgreSQL
  • Qdrant
  • MCP

Technical challenges

  • No transaction spans PostgreSQL, Qdrant and the checkpoint.
  • A long-running sync has to cope with rate limits (flood-wait) and retries.

Design decisions

  • Writes are idempotent: deterministic UUIDv5 point IDs, and the cursor is saved only after each upsert.
  • Transcription workers claim queue rows with SKIP LOCKED, so several workers can run in parallel.

Reliability considerations

  • After a failure, the sync resumes from the last saved cursor. Repeated upserts overwrite the same points, so they are harmless.
