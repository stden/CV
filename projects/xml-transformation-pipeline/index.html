Work project

XML Transformation Pipeline

Asynchronous XML routing and XSLT transformation with Java extension functions loaded from plugins.

Engineering context: Kuehne+Nagel, iOPM (work)

Problem

Upstream systems send XML requests that must be routed and transformed before reaching their destinations, and failed messages must not be lost.

Architecture

Messages arrive on RabbitMQ and are routed to destination queues. XSLT stylesheets transform them. Stylesheets call Java extension functions from plugin jars, each loaded by its own classloader. Failed messages go to a separate error path.

Architecture diagram

  1. Upstream systems. Producers of XML requests.
  2. Request queue. Decouples producers from processing; messages are not processed inline.
  3. Router. Routing is a separate step, so it can change without touching transformations.
  4. XSLT transformer. Transforms the message. Each plugin jar has its own classloader.
  5. Destination queues. Delivery to the consuming systems.
  6. Failure path. Failure handling: a message that cannot be processed is not lost.

Component names are generic. Concepts used here: delivery guarantees, failure handling.

Technology stack

  • Java
  • Spring AMQP
  • RabbitMQ
  • Saxon XSLT
  • JDBC

Technical challenges

  • Plugin classloading and hot reload.
  • Handling failed messages without losing them.

Design decisions

  • Each plugin jar gets its own classloader, so plugins can be replaced and the context reloaded without restarting the service.
  • Routing and transformation are separate steps, so each can change on its own.

Reliability considerations

  • Failed messages are kept and handled through a separate error path instead of being dropped.
